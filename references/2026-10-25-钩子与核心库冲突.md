# 2026-10-25：DSH 钩子与重复核心库冲突复盘

本篇记录 Windows 桌面版 DSH `0.2.1-rc.3` 的一次实测故障。机制依据同版本官方资料，修复过程和结果来自本机验证；包名、数量和版本是当时的证据，不是以后照搬的清理清单。

## 故障是怎样发生的

桌面版升级插件、处理钩子桥接依赖后，profile 中额外直接安装了桌面程序本已提供的核心库。独立导入钩子包能够成功，但重启后所有工具在执行前报错：

```text
Cannot read properties of undefined (reading 'prepare')
```

当时先凭发生顺序归因为“钩子不兼容”，要求用户手动删配置；随后又把停用钩子、恢复普通工具当作阶段终点。这两个判断都不充分：导入成功没有验证运行时调度，时间先后也不能证明故障出在钩子；用户要求恢复功能时，临时停用并未完成任务。

本次必须区分三件事：核心调度的重复库冲突、本地钩子脚本的输出协议错误，以及排查时验证脚本本身的接口误用。

## 官方机制与本机证据

### 核心库为何会冲突

官方加载规则保留 Node 的祖先目录查找顺序。profile 内实际安装的包先于共享运行时所在的位置命中；桌面程序自身的导入则使用安装包里的核心库。因此，即使版本号相同，profile 与桌面安装包也可能加载两份独立模块。

同版本 `dsh-tools` 为调度器使用模块内创建的 `Symbol`，两份模块的标识并不相同；`agent-loop` 按自己导入的标识读取调度器，再直接调用 `.prepare()`。标识不匹配时，读到的是 `undefined`，调用即失败。

本机验证与此一致：

1. 会话日志出现工具调用后立即结束该轮，报上述错误。
2. 仅停用 `hooks-claude-code` 后，调度器 `prepare` 仍不可用。
3. 仅移除额外核心库的依赖声明后，实体目录仍在，错误仍存在。
4. 备份并移出冲突实体副本后，`prepare` 恢复为函数，内置文件读取成功。

这支持“重复核心库触发调度缺陷”的判断，不能据此说官方钩子插件无法使用。官方代码对冲突的处理不完善，与这次额外安装副本的触发条件要分别说明；官方仓库中的用户讨论也不能冒充维护者已确认或已修复的公告。

### 本次移出了哪些额外副本

以下 8 个包在本次 profile 与桌面安装包中重复存在，均属于 `@deepseek-ai/`：

```text
cordis
dsh-agent
dsh-llm
dsh-session
dsh-session-projection
dsh-subagent
dsh-tools
dsh-working-directory
```

先停止目标 DSH，复制并逐文件校验备份，再将额外实体副本移入集中备份目录；本次校验了 3219 个文件，没有永久删除这些副本。同步移除 `package.json` 和锁文件 importer 中对应的直接依赖声明，保留其他插件版本与 bundle 顺序。钩子桥接和协议包本身保留。

以后要先核实当次真实加载来源、调用关系和官方运行时提供的内容。不要看到 `@deepseek-ai/` 前缀就批量移走，也不要把第三方 `dsh-shared` 缺导出的修复办法套成批量补装官方核心库。

### 钩子脚本还有一处协议错误

本地 `pre-tool.ps1` 把拦截决定和中文理由写到 stdout 的 JSON 中，却使用退出码 `2`。同版本官方解码器规定：

- 退出码 `0`：解析 stdout 中的结构化 JSON，可通过 `hookSpecificOutput.permissionDecision` 返回 `deny` 及理由。
- 退出码 `2`：按阻断处理，理由来自 stderr；不会把 stdout JSON 当作结构化决定读取。
- 其他退出码或进程执行失败：按非阻断错误处理，不能把脚本异常当作有效拦截。

本次保留原有拦截规则，只把返回结构化决定后的退出码改为 `0`，并修正对应注释。脚本原有 UTF-8 BOM 和 CRLF 保持不变，中文理由正常返回。原脚本在无控制台环境中使用原始标准流按 UTF-8 读写，没有为此改成依赖控制台编码的实现。

## 排查中走错的步骤

- **只看最新 README，忽略实际版本。** 最新分支的工具接口已经可能不同于已安装版本。先核实版本，再读对应发布标签和安装包代码，不能把最新接口直接套到旧运行时。
- **凭印象写验证接口。** 曾遗漏工具调用必需的取消信号，导致验证程序报读取 `aborted` 的错误；还把 Schemastery 的配置对象当成其他校验库，调用了不存在的 `Config.parse()`。官方 Schemastery 文档说明配置对象可以直接作为函数调用。这些是验证程序错误，不是 DSH 又出现了新的故障。
- **把根服务当成完整会话。** Web 的文件工具按 Agent preset 组合，直接访问根服务可能没有 `read`，不能把 `UNKNOWN_TOOL` 当成插件坏了。
- **用无 Agent 的调用验证修改放行。** 官方文件观察策略按 Agent 会话记住读取状态；无会话的调用即便读过，也不能满足修改前观察要求，会报 `FS_NOT_OBSERVED`。这与“是否存在备份”的本地钩子规则是两套检查，不能混淆。
- **恢复普通工具后就停下。** 用户已授权恢复钩子，清除冲突后应继续启用、测试和重启检查，不需要再重复询问是否继续。只有确实遇到范围变化、必要权限缺失或有证据支持的上游阻碍，才说明具体未完成项。

## 最终怎样验收

使用桌面版自带运行时、同一 `desktop` 配置、真实 Agent 会话、官方钩子桥接和内置文件工具，在当前工作目录的 `work` 中创建唯一测试文件，完成以下六项检查：

1. 新建文件放行。
2. 覆盖已有文件被钩子拦截，中文理由正确，文件哈希不变。
3. 没有备份的修改被钩子拦截，中文理由正确，文件哈希不变。
4. 普通读取放行。
5. 完成并校验备份、通过工具读取文件后，修改放行，内容符合预期。
6. 拦截后普通工具仍然正常。

六项均通过，核验进程退出码为 `0`。测试未发送模型请求，也没有用真实业务文件试覆盖或删除；测试文件按当次文件保护规则保留。

上述六项测试是在修复冲突和协议错误、恢复桥接启用后执行的。测试通过后，再从原桌面版快捷方式重启并显示原会话。重启后读取运行中的状态，确认桥接为 `live`，其余 5 个插件版本不变且均已加载，技能中心正常响应，插件错误和诊断问题均为 `0`。当时技能数为 `179`；该数量和端口不能作为以后固定的验收值。
